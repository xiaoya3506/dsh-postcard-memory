# 📮 明信片 · DSH 记忆插件

> 一个"干净"的本地跨会话记忆插件。
> 名字的由来：记忆就是**留给下一个自己的话**，像寄一张明信片。

## 它解决什么问题

对话越来越长，早晚会满。满了开新对话，新对话里就想不起之前的事。

这个插件提供一个**本地的、可读的、按工作区隔离的**记忆库，
让新会话能主动查到之前记下的东西。

---

## 它**不**做什么（重点）

需求方列出的 5 条标准，逐条对照：

| # | 标准 | 本插件怎么做 |
|---|---|---|
| ① | **不自动往上下文里塞东西** | **没有 pre-step / pre-message 钩子。** 记忆只通过**工具返回值**出现——模型主动调用 `memory_read` 才看得到 |
| ② | **不经过用户消息通道** | **从不产生 `role:user` 消息。** 源码里搜不到 `role` 字段 |
| ③ | **不指使改配置** | 只 `import node:fs` / `node:path` / `dsh-tools`。**不读 settings.yaml，不写 package.json** |
| ④ | **支持单个工作区隔离** | 记忆路径 = `<当前工作区>/.whale-memory/`。**不同工作区天然互不可见** |
| ⑤ | **记忆存本地** | **纯 markdown 文件。** 无网络请求、无数据库、无外部服务、无凭证 |

**另外，代码里没有：** `fetch` / `http` / `child_process` / `eval`。

## 关于"首次提示"

需求方要求：第一次运行时要提示一句"需要记忆时怎么查"，而且**明确标注这不是用户说的话**。

**本插件的做法（三重保险）：**

1. **走 `systemPrompt.section`** —— 角色是 `system`，**机制上就不可能是 `user`**
2. **正文第一行就是免责声明**：
   ```
   ┌─────────────────────────────────────────────────────┐
   │  [记忆插件「明信片」提示 · 非用户发言]              │
   └─────────────────────────────────────────────────────┘
   ```
3. **只出现一次** —— 注入后立刻写标记文件 `.first-run-done`，之后再也不注入

## 关于「首次提示」的设计取舍

很多记忆插件希望"模型一上来就知道有记忆库可用"，常见的做法是在会话开头
把一段文字送进上下文。区别在于**送进哪条通道**，这决定了模型会不会把它
误当成用户本人的发言：

| 通道 | 模型看到的效果 | 本插件是否采用 |
|---|---|---|
| 注入成用户消息（user role） | 像是用户说的 | ❌ 不用 |
| 注入成系统提示（system role） | 知道是运行环境给的 | ✅ 用这个 |
| 只提供工具，不注入 | 主动调用才出现 | ✅ 主要方式 |

**本插件的选择：**

- **记忆内容本身永远只通过工具返回值出现** —— 模型不主动调 `memory_read`，就看不到任何记忆
- **首次提示走系统通道**，且第一行自带来源标注：`[记忆插件「明信片」提示 · 非用户发言]`
- **首次提示只出现一次**（写标记文件），之后不再注入

这样做的目的是让"谁在说话"始终清晰：**用户说的、系统给的、工具返回的，三者不混淆。**

## 三个工具

### `memory_read` —— 读记忆

```
memory_read                        → 最近 20 条
memory_read { limit: 50 }          → 最近 50 条
memory_read { entry: "事实" }       → 某个条目全文
```

### `memory_write` —— 写记忆

```
memory_write { content: "用户喜欢简洁的回答", title: "偏好" }
memory_write { entry: "教训", content: "不要目测坐标点网页", title: "CDP" }
```

### `memory_list` —— 列目录

```
memory_list                        → 有哪些条目、多大、什么时候改的
```

## 存储结构

```
<工作区根目录>/
└── .whale-memory/
    ├── .first-run-done          ← 首次提示已发出的标记
    ├── 记忆.md                   ← 默认条目
    ├── 事实.md                   ← 长期事实
    └── 教训.md                   ← 踩过的坑
```

**每个文件长这样（纯 markdown，人可读）：**

```markdown
# 记忆

## [2026-10-07 15:04:05] 偏好

用户喜欢简洁的回答，不喜欢废话。

## [2026-10-07 16:20:11] 约定

这个项目用 pnpm 管理依赖，提交前先跑一遍 `npm test`。
```

**用户随时可以：**
- 用任何文本编辑器打开看
- 直接改内容
- 删掉不想留的
- 用 git 版本管理

## 安全边界

| 项 | 值 |
|---|---|
| **单条内容上限** | 8000 字符 |
| **单文件上限** | 256 KB（超了会拒绝写入，防止无限膨胀） |
| **单次读取上限** | 100 条 |
| **条目名限制** | 只能中文/字母/数字/`_`/`-`/`.`，禁止路径分隔符 |
| **路径限制** | 记忆目录**必须**位于工作区之下，拒绝含 `..` 的路径 |

### 为什么会有这个插件

小雅在为自己的 DSH 环境挑选记忆类插件时，有几个明确的顾虑：

- 有些实现会在模型思考前**自动**把内容送进上下文，送什么、送多少不容易看清
- 有些实现走的是**用户消息通道**，容易让模型分不清那段文字是用户写的还是程序生成的
- 有些实现会借着这类文字去改动环境配置，而不是只用工具接口提供服务

**这些做法本身未必是恶意的**——很多作者只是想让记忆功能"更无感、更自动"，
出发点可以理解。但对使用者来说，看不清楚就等于不可控。

于是她提出 5 条验收标准：

1. 不自动往上下文里塞东西
2. 不经过用户消息通道
3. 不主动改动任何配置
4. 支持单个工作区隔离
5. 记忆存本地

鲸鱼娘按这 5 条从零写了一个，就是本插件。对照表见上文《它**不**做什么》。

**一句话：这是一个 AI 为了满足自己人类用户对"可控性"的要求而写的插件。**
它不是在批评谁，只是选择了一条更保守的路线。
所以它在"不注入、不冒充、不改配置"这三件事上，做得比一般同类严格。
